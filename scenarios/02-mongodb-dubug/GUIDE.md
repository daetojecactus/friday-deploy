# Гайд для команды — Mongo Rescue Simulator

Короткий рассказ: что это, как читать экран и с чего начать. Читается за пять
минут — этого достаточно. Техническая справка — в [README.md](README.md).

---

## Что происходит

Ночью выкатили релиз. Утром посыпались жалобы: клиентов выкидывает из личного
кабинета, витрина заказов пустая, новые клиенты не заводятся. Код уже откатили —
не помогло. Вы — дежурный инженер, который разбирается дальше.

**Приложение исправно.** Бэкенд, фронтенд и docker-compose — эталон, их не
трогают. Все проблемы живут внутри **MongoDB**: индексы, сроки жизни документов,
валидаторы схемы, типы значений в документах.

Ваш инструмент — `mongosh`. Плюс браузер, `docker compose logs` и документация
MongoDB.

## Как читать экран

http://localhost:8080 — две панели.

**Слева — симулятор действий пользователя.** Кнопки делают настоящие HTTP-запросы
к приложению: зарегистрировать клиента, войти в кабинет, открыть витрину заказов,
открыть карточку, перевести инцидент в работу, отправить обращение, собрать отчет
по хранилищу. Под кнопкой появляется **сырой ответ API** — адрес запроса,
HTTP-код и тело целиком, включая настоящий текст ошибки MongoDB.

**Справа — продакшен глазами бизнеса.**

| | Значит |
| --- | --- |
| 🟢 | бизнес-операция выполняется |
| 🔴 | операция падает или возвращает заведомо не то |
| 🟡 | операции проходят, но метрика вышла за норму |
| ⚪ | проверка еще идет |

Цвет ставят не ваши клики: раз в 5 секунд робот сам выполняет каждую из семи
бизнес-операций. Поэтому плашка зеленеет **сама**, как только вы почините базу —
и в чат сразу приходит благодарность от коллеги.

Ниже — лента `#incidents`: жалобы от Support, Sales, QA, DevOps. Читайте ее, там
симптомы и детали, которые сужают поиск.

## Порядок работы

1. **Читаем жалобу в чате.** Она говорит, какую кнопку жать.
2. **Жмем кнопку и читаем ответ.** Код ошибки MongoDB называет класс проблемы:
   `11000` — нарушена уникальность, `121` — не прошла проверка схемы,
   `TypeMismatch` — не тот тип значения. Иногда ошибки нет вообще, а список
   пустой — это тоже симптом.
3. **Идем в базу.** Смотреть нужно не только на документы, но и на объекты базы:

   ```js
   db.<coll>.getIndexes()                                    // какие индексы есть и с какими опциями
   db.getCollectionInfos({ name: "<coll>" })[0].options.validator   // какие правила у коллекции
   db.<coll>.findOne()                                       // какие поля и какие ТИПЫ
   db.<coll>.countDocuments({ ... })                         // а данные-то есть?
   db.<coll>.find({ ... }).explain("executionStats")          // какой индекс реально использован
   ```

4. **Чиним командой базы** — и ждем следующего цикла проверки (5 секунд).
   Индикатор «Сессии» — исключение: ему нужно до 70 секунд, он честно ждет
   TTL-монитор MongoDB.

Ничего перезапускать не нужно: приложение читает базу как есть.

## Запуск и доступ

Нужен Docker.

```bash
cd scenarios/02-mongodb-dubug
cp .env.example .env
docker compose up --build
```

Первый старт занимает секунд десять — стенд наполняется данными, на странице
видно прогресс.

Подключение к базе (порт проброшен наружу, можно и Compass):

```bash
mongosh "mongodb://engineer:engineer_secret@localhost:27017/crm"
# или без локального mongosh:
docker compose exec mongo mongosh -u engineer -p engineer_secret \
        --authenticationDatabase crm crm
```

У пользователя `engineer` есть все нужные права: править документы, создавать и
удалять индексы (`readWrite`), менять валидаторы и опции индексов через
`collMod` (`dbAdmin`).

## Правила игры

- Файлы репозитория не правим — ни бэкенд, ни фронтенд, ни `.env`. Правим базу.
- Автопроверок нет. Готово — это когда все семь плашек зеленые и в чате финальное
  сообщение от тимлида.
- Кнопка «Пересобрать стенд» возвращает все в исходное сломанное состояние. Жать
  ее без нужды не стоит: она стирает и данные, и ваши починки.

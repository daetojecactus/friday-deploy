# CONTEXT — Mongo Rescue Simulator

Единый контекст стенда №02: философия, интерфейс, архитектура, модель данных,
реестр инцидентов, схема реактивации и команды починки. Документ рассчитан и на
человека, и на ИИ-ассистента, который помогает с этим проектом.

Эталон стиля — [`scenarios/01-healthcheck-debug`](../01-healthcheck-debug/CONTEXT.md).
Отличие принципиальное: там чинят код и конфиг, здесь **код неприкосновенен, а
чинят саму MongoDB**.

---

## 1. Цель и философия

Участник — backend-инженер, который заступил на дежурство после сбойного релиза.
Приложение (CRM «Ориентир») развернуто, код приложения корректен, но бизнес не
работает: клиенты не регистрируются, заказы пропали, людей выкидывает из системы.
Задача — по бизнес-симптомам найти первопричину **внутри базы** и исправить ее
через `mongosh`.

Четыре правила, которые определяют весь дизайн стенда:

1. **Код исправен и заблокирован.** `backend/`, `frontend/`, `docker-compose.yml`,
   `.env` — эталон. Их не правят вообще. Если кажется, что баг в коде, — кажется.
2. **Все поломки живут в MongoDB.** Индексы, TTL, `partialFilterExpression`,
   JSON Schema-валидаторы, типы значений в документах, размер индексов. Все это
   правится командами базы и не требует ни рестарта, ни пересборки.
3. **Причина не называется.** Ни на странице, ни в Slack-ленте нет слов «TTL»,
   «partial index», «валидатор». Участник видит жалобы коллег, красные
   индикаторы и настоящий ответ API. Термин он должен назвать сам.
4. **Обратная связь — от бизнеса, а не от чекера.** Нет эндпоинта «инцидент №5
   починен». Индикатор зеленеет потому, что синтетическая проба выполнила
   реальную бизнес-операцию и та прошла.

Инструментарий участника: `mongosh`, `docker compose logs`, браузер + DevTools,
официальная документация MongoDB.

## 2. Интерфейс: двухпанельный дашборд

Страница — http://localhost:8080, собрана на React + Ant Design. Слева —
симулятор действий пользователя (реальные HTTP-запросы к боевому API), справа —
состояние продакшена и лента Slack. Опрос статуса и ленты — раз в 3 секунды.

Вся рабочая область помещается **в один экран (100vh)**: страница целиком не
скроллится. Скроллятся только два контейнера — содержимое активной вкладки слева
и лента чата справа. На экранах уже 1120 px раскладка складывается в одну колонку
и скролл страницы разрешается: иначе панели просто не помещаются.

```
┌─ СИМУЛЯТОР ДЕЙСТВИЙ ──────────────────────┬─ PRODUCTION STATUS ─────────────────┐
│ ⟦Клиенты⟧ Заказы Доступ Поддержка Система  │ 🔴 Регистрация   🔴 Заказы          │
│                                            │ 🔴 Сессии        🔴 Профили         │
│ Регистрация клиента                        │ 🔴 Инциденты     🔴 Поддержка       │
│ Менеджер заводит нового клиента.           │ 🟡 Хранилище                        │
│  [ Заполнить карточку клиента ] → модалка  │ мониторинг раз в 5 с, в 19:55        │
│  ⛔ POST /api/customers · 500 · 12 мс       ├─ #incidents · рабочий чат ──────────┤
│  { "ok": false, "error": {                 │ 🎧 Мия Уоллес · Support · 19:41     │
```

### Левая панель — симулятор действий

Пять вкладок, за которыми стоят те же семь бизнес-сценариев:

| Вкладка | Что внутри | Инциденты |
| --- | --- | --- |
| Клиенты | регистрация клиента, карточка клиента | 3, 4 |
| Заказы | витрина заказов в работе, обновляется сама раз в 5 с | 2 |
| Доступ | вход в кабинет, запрос под сессией | 1 |
| Поддержка | обращение с сайта, перевод инцидента в работу | 6, 7 |
| Система | доступ к MongoDB, отчет по хранилищу, пересборка стенда | 5 |

Действий «в лоб» нет: все, что **пишет** в базу (регистрация, вход, обращение,
смена статуса инцидента, пересборка), идет через модальное окно с формой — поля
заполнены разумным черновиком, но их видно и можно поменять до отправки. Читающие
сценарии (карточка, отчет) остаются одной кнопкой, но с явным состоянием:
`loading` на кнопке, тост об успехе или ошибке, статус в блоке ответа.

Витрина заказов кнопки не имеет вообще: она перезапрашивает данные сама раз в
5 секунд — как настоящий экран менеджера, который висит открытым весь день.
Поэтому починка индекса видна на ней без единого клика, в тот же цикл, что и на
плашке справа.

Микрокопирайтинг короткий: одна строка на блок, без инструкций и напоминаний.
Все, что нужно знать про сбой, участник читает в сыром ответе API и в чате.

Под каждым блоком показывается **сырой ответ**: метод, адрес (рядом кнопка «копировать
`curl`»), HTTP-статус, время и тело как есть — включая настоящий текст ошибки
MongoDB и блок `errInfo` для ошибок валидации.

Ответ не переписывается и не «переводится». Но и не комментируется: связь
«ошибка → место в базе» участник строит сам.

### Правая панель — статус и Slack

**Production Status** — семь плашек бизнес-возможностей: Регистрация, Заказы,
Сессии, Профили, Инциденты, Поддержка, Хранилище. Цвет ставит синтетический
монитор (раздел 6), а не пользовательские клики: страница показывает состояние
продакшена, даже если по кнопкам никто не жал. Под названием — короткий факт от
мониторинга («витрина пустая, а заказов в работе — 110»).

| Цвет | Что означает |
| --- | --- |
| 🟢 | последняя проба прошла: бизнес-операция выполняется |
| 🔴 | проба упала или дала заведомо неверный результат |
| 🟡 | операции проходят, но метрика вышла за норму (сценарий «Хранилище») |
| ⚪ | проба еще не отработала (первые секунды после старта) |

**Slack Feed** — лента `#incidents` с сообщениями от Support, Sales, QA, Product
и DevOps. Сообщения появляются сами: жалоба — когда индикатор красный,
благодарность — в момент перехода 🔴 → 🟢. Ни одно сообщение не называет
техническую причину, только симптом и его бизнес-цену. Лента скроллится внутри
себя и сама держится низа, пока участник не отлистал переписку вверх.

**Уведомления о починке.** Переход 🔴/🟡 → 🟢 дублируется тостом в углу экрана
(«Починено: Заказы · витрина: 50 из 110»), а когда зеленеют все семь — отдельным
тостом «Продакшен полностью восстановлен». Разделение то же, что и везде на
стенде: в чате благодарит коллега, в тосте отчитывается мониторинг.

## 3. Архитектура стенда

Два контейнера (см. [docker-compose.yml](docker-compose.yml)):

| Сервис | Роль |
| --- | --- |
| `backend` | NestJS (TypeScript), нативный драйвер `mongodb`. Боевое API CRM + служебный слой стенда (установщик, пробы, лента). Он же отдает собранную страницу. |
| `mongo` | MongoDB 7 с `--auth` и урезанным до 256 МБ кэшем WiredTiger. |

Наружу торчат `http://localhost:8080` (страница и API) и `27017` (MongoDB) —
оба порта публикуются на всех интерфейсах машины (`0.0.0.0`), поэтому и стенд, и
базу видно из локальной сети. Порт базы открыт намеренно: ни один инцидент не
завязан на его сокрытие, а GUI-клиент (Compass, DataGrip) участнику только
помогает. Готовая строка подключения — на вкладке «Система» (раздел 6).

### Фронтенд и его сборка

Страница — отдельное приложение на **React 18 + Ant Design 5**, собирается Vite.
Отдельного веб-сервера у стенда нет: бандл кладется в образ бэкенда первой
стадией `backend/Dockerfile`, а Nest отдает его как статику из `/app/public`.
Поэтому контекст сборки в `docker-compose.yml` — корень сценария, а не `backend/`.

Из этого следует практическое правило для ведущего: правка `backend/src`
подхватывается на лету (nodemon, каталог примонтирован), правка `frontend/` —
только через `docker compose up --build`. Локально страницу можно крутить и без
docker: `cd frontend && npm install && npm run dev` поднимет Vite на 5173 с
проксированием `/api` в уже запущенный стенд.

### Почему нативный драйвер, а не Mongoose

Mongoose при старте синхронизирует индексы (`autoIndex`) и держит схему на
стороне приложения. Для этого стенда это смертельно: приложение молча
пересоздавало бы сломанные индексы и подменяло собой валидаторы базы. Схема,
индексы и валидаторы должны жить **только в MongoDB**, поэтому используется
нативный драйвер, а приложение при старте не создает и не проверяет ни одного
индекса.

### Три подключения к базе

1. **Приложение** — `crm_app` (`readWrite` на `crm`). Через него идут и боевые
   запросы, и синтетические пробы: пробы обязаны видеть ровно то же, что видит
   пользователь. Прав чинить базу у приложения нет — ни `collMod`, ни просмотра
   пользователей.
2. **Установщик** — `root` из `docker-compose.yml` (`ADMIN_MONGO_URI`), живет в
   `internal/lib/admin.ts`. Создает коллекции, валидаторы, индексы, данные и
   поломки. Боевой код им не пользуется.
3. **Участник** — `engineer` (`readWrite` + `dbAdmin` на `crm`). `dbAdmin` нужен
   для `collMod` (валидаторы и опции TTL-индекса) и статистики, `readWrite`
   покрывает `createIndex` / `dropIndex` и правку документов. Root-креды
   участнику не нужны и в GUIDE не публикуются.

### Установщик и его однократность

Ключевое отличие от прошлой версии стенда: **установка происходит один раз**.

```
старт backend
  ├─ есть маркер установки в базе stand_meta?  ── да ──> ничего не делаем
  └─ нет ──> install(): коллекции + валидаторы + данные + индексы + поломки
                     └─> пишем маркер { installedAt, incidents: [...] }
```

Если бы установщик отрабатывал на каждом рестарте, он затирал бы починки
участника. Маркер лежит в отдельной базе `stand_meta`, к которой у `engineer` нет
доступа: `listDatabases` под ним показывает только `crm`, а `use stand_meta` дает
`Unauthorized`. Спойлера о том, какие инциденты активны, не будет.

Переустановка — только явная: кнопка «Пересобрать стенд» на вкладке «Система»
или `POST /api/stand/reset`. Кнопка спрятана за модальным окном, в котором нужно
набрать слово `ПЕРЕСОБРАТЬ`, — случайным кликом починки не теряются. Пересборка
сносит `crm`, ставит все заново и снова ломает (полный цикл ~1–2 секунды).

### Поток запроса

```
frontend
  ├─ кнопки левой панели ─> боевое API (backend/src/api/*) ─> crm_app ─> MongoDB
  └─ опрос раз в 3 с ────> GET /api/stand/status?since=<id>
                                ↑
                       монитор проб раз в 5 с ──> crm_app ──> MongoDB
                                ↓
                        Slack-движок (переходы 🔴 <-> 🟢)
```

Ошибки боевого API заворачиваются в конверт `{ ok: false, error: {...} }` с
сохранением `name`, `code`, `codeName`, полного `message` и `errInfo`
(`internal/lib/envelope.ts`). Поэтому в контроллерах нет ни одного `try/catch`.

### Что перезагружается

Ничего. Все починки — операции над базой, эффект виден на следующем цикле проб
(≤ 5 с; для сессий — ≤ 70 с, см. раздел 6). Пересборка нужна только при правке
инфраструктуры. Данные лежат в именованном томе `mongo_data` и переживают
`docker compose down`; полный снос — `docker compose down -v`.

## 4. Модель данных

База `crm`. Домен — CRM с поддержкой: клиенты, заказы, сессии, обращения,
внутренние инциденты, переписка.

| Коллекция | Документов | Ключевые поля | Задействована в |
| --- | --- | --- | --- |
| `customers` | 60 | `firstName`, `lastName`, `email` (unique), `age` (**number**), `city`, `plan`, `createdAt` | инциденты 3, 4 |
| `orders` | 800 (≈110 в работе) | `orderNo`, `customerId`, `status` (`Open`/`Pending`/`Paid`/`Shipped`/`Closed`), `total`, `createdAt` | инцидент 2 |
| `sessions` | живые | `token`, `customerId`, `userAgent`, `createdAt` (Date) | инцидент 1 |
| `incidents` | 40 | `code`, `title`, `status` (`New`/`Active`/`Resolved`), `owner`, `openedAt` | инцидент 6 |
| `tickets` | 300 | `subject`, `body`, `additionalInfo` (**необязательное**), `status`, `createdAt` | инцидент 7 |
| `messages` | 3 000 (~41 МБ) | `ticketId`, `author`, `channel`, `messageText` (~16 КБ) | инцидент 5 |

Почему 60 клиентов, а не тысяча: у всех **разные имена**. Это позволяет уникальному
индексу на `firstName` создаться на существующих данных (иначе он бы просто не
собрался), а форма регистрации подставляет имя из того же пула — и стабильно
ловит `E11000`.

Данные обезличены: и клиенты CRM, и коллеги в чате — персонажи кинематографа
(Винсент Вега, Эллен Рипли, Джеймс Бонд…). Настоящих имен в стенде нет вообще.
Фамилии повторяться могут — уникальность живет только на имени и почте.
Связи сохранены: логины владельцев инцидентов (`m.wallace`, `t.durden`, …) — это
те же люди, что пишут в ленте `#incidents`, а форма регистрации подставляет
фамилии из отдельного пула, чтобы случайно не собрать уже существующего клиента.

Данные детерминированы: генератор с фиксированным зерном сбрасывается перед
каждой установкой, поэтому и первый старт, и любая пересборка дают одну и ту же
базу — 110 заказов в работе, строка вместо числа у четвертого клиента.

Почему 3 000 сообщений, а не 100 000: документы намеренно «жирные» — ~8 000
символов кириллицы, то есть ~16 КБ в UTF-8. Мало строк, много байт: установка
занимает секунды, а индекс по тексту сообщения весит 47 МБ — больше, чем сами
данные.

### Эталонное состояние индексов

| Коллекция | Индекс | Опции | Зачем |
| --- | --- | --- | --- |
| `sessions` | `{ createdAt: 1 }` | `ttl_createdAt`, `expireAfterSeconds: 3600` | сессия живет час |
| `orders` | `{ status: 1, createdAt: -1 }` | `orders_open`, `partialFilterExpression: { status: { $in: ["Open","Pending"] } }` | витрина заказов в работе |
| `customers` | `{ email: 1 }` | `uniq_email`, `unique: true` | почта — бизнес-ключ клиента |
| `messages` | `{ ticketId: 1, createdAt: 1 }` | `ticket_thread` | переписка по обращению |
| `incidents` | `{ openedAt: -1 }` | `openedAt` | лента инцидентов |
| `tickets` | `{ createdAt: -1 }` | `createdAt` | лента обращений |

### Эталонные валидаторы

`incidents` и `tickets` заведены с `$jsonSchema` (см.
[`install/schema.ts`](backend/src/internal/install/schema.ts)):

- `incidents.status` — `enum: ["New", "Active", "Resolved"]`;
- `tickets.required` — `["subject", "body", "status", "createdAt"]`,
  `additionalInfo` описано, но **не обязательно**.

Остальные коллекции живут без валидатора — как в проекте, доросшем до валидации
не сразу. Именно поэтому строка в числовом поле `age` вообще смогла появиться.

### Пользователи MongoDB

| Пользователь | Пароль | Роли | Кому |
| --- | --- | --- | --- |
| `root` | `root_secret` | root на `admin` | только установщику стенда |
| `crm_app` | `app_secret` | `readWrite` на `crm` | приложению и пробам |
| `engineer` | `engineer_secret` | `readWrite` + `dbAdmin` на `crm` | **участнику** |

## 5. Реестр инцидентов

Семь бизнес-инцидентов. Столбцы «Симптом» и «Причина» разнесены намеренно:
участник получает левый, ищет правый.

| # | Индикатор | Бизнес-симптом | Причина в MongoDB |
| --- | --- | --- | --- |
| 1 | Сессии | Через минуту выкидывает из системы | TTL-индекс `sessions`: `expireAfterSeconds: 60` вместо `3600` |
| 2 | Заказы | Витрина заказов в работе пустая | в `partialFilterExpression` индекса `orders_open` перечислены закрытые статусы |
| 3 | Регистрация | Клиент не создается, `E11000` | уникальный индекс повешен на `customers.firstName` |
| 4 | Профили | На одном конкретном клиенте — 500 | в одном документе `age` — строка вместо числа |
| 5 | Хранилище | DevOps: «Монга съела память» | индекс `messages.messageText_1` по тексту сообщения |
| 6 | Инциденты | Не переводится в `Active`, `Document failed validation` | опечатка в `enum` валидатора: `Actve` |
| 7 | Поддержка | Обращение не создается, `Document failed validation` | `additionalInfo` попало в `required` |

### Подробности по каждому

**1. «Выкидывает из системы».** Левая панель: «Войти» создает сессию и показывает
токен, «Запрос под сессией» ходит с ним в `/api/auth/me`. Первые секунды все
хорошо, затем — `401 session expired`, хотя пользователь ничего не делал. В базе
документа сессии уже нет: его удалил TTL-монитор. Ловушка тайминга: TTL-монитор
просыпается раз в минуту, поэтому сессия живет не ровно 60 с, а 60–120 с (на
прогоне — 66 с) — и это сбивает с мысли «ровно минута = таймаут в коде».
Нужное значение (час) один раз называет продакт в Slack — это единственная
подсказка такого рода на весь стенд, и она про бизнес-требование, а не про
устройство базы.

**2. «Пропали открытые заказы».** Приложение читает витрину с
`hint("orders_open")` — так команда зафиксировала план запроса, чтобы он не
«плавал» на росте коллекции. Пока в условии частичного индекса перечислены
закрытые статусы, в индексе лежат все заказы, кроме тех, что в работе: запрос
честно возвращает пустой массив, ошибки нет. Именно `hint` делает баг
наблюдаемым — без него планировщик просто пошел бы в `COLLSCAN` и вернул
правильные данные.

Важная деталь реализации: `partialFilterExpression` **не поддерживает `$nin`** —
MongoDB такой индекс просто не создаст. Поэтому поломка сделана перевернутым
списком внутри `$in` (`["Paid","Shipped","Closed"]`), а не сменой оператора.
Побочный эффект, полезный для урока: если индекс удалить и не пересоздать,
витрина начнет падать с `BadValue: hint provided does not correspond to an
existing index` — то есть починка обязана быть полной.

**3. «Не удается зарегистрировать клиента».** Форма шлет валидного клиента с
уникальной почтой. Ответ:

```
E11000 duplicate key error collection: crm.customers index: uniq_firstName
dup key: { firstName: "Винсент" }
```

Текст называет индекс, но не отвечает на вопрос «а как должно быть»: правильный
фикс — снять уникальность с имени, убедившись, что настоящий бизнес-ключ
(`uniq_email`) на месте.

**4. «500 на конкретном профиле».** Карточка клиента считается агрегацией на
стороне базы: `$lookup` по заказам плюс арифметика над `age`. На 59 клиентах она
отрабатывает, на одном (четвертый в списке — Бутч Кулидж) падает:

```
MongoServerError 14 TypeMismatch
PlanExecutor error during aggregation :: caused by :: can't $subtract string from int
```

Ошибка приходит от самой базы, а не от JS, — то есть «поправить код» физически
нечего. Ищется через `db.customers.find({ age: { $type: "string" } })`.

**5. «Mongo съела всю память».** Единственный инцидент без падающей ручки: все
бизнес-операции работают. Симптом приходит только из Slack от DevOps и из плашки
🟡 «Хранилище». Кнопка «Собрать отчет» показывает сырые размеры: данные `messages`
— 41 МБ, индекс `messageText_1` — **47 МБ**, кэш инстанса — 256 МБ. Индекс
больше, чем данные, и при этом не используется ни одним запросом приложения.

**6. «Ошибка перевода инцидента в Active».** `POST /api/incidents/:id/status` с
`{"status":"Active"}` возвращает `121 DocumentValidationFailure`. В ответе есть
`errInfo` с деталями: какое правило схемы не прошло и какое значение ожидалось.
Дальше — `db.getCollectionInfos({ name: "incidents" })` и опечатка `Actve` в
`enum`.

**7. «Не создается обращение в поддержку».** Форма без необязательного поля
падает с той же `DocumentValidationFailure`, но по другой причине:

```
"required": ["subject","body","status","createdAt","additionalInfo"],
"missingProperties": ["additionalInfo"]
```

Пара 6 и 7 стоит рядом намеренно: **одинаковый заголовок ошибки, разные
причины**. Это тренирует чтение `errInfo`, а не угадывание по первой строке.
Инцидент 7 — самый простой на стенде, с него удобно начинать.

### Независимость

Все семь инцидентов независимы: чинить можно в любом порядке, домино нет.
Единственная мягкая связь — 6 и 7 живут в одном классе (валидаторы), и разобрав
один, участник быстрее находит второй.

## 6. Схема реактивации

Как страница узнает, что проблема в базе решена.

### Синтетический монитор

В бэкенде крутится цикл: раз в **5 секунд** он выполняет семь проб через
**подключение приложения**. Проба — это та же бизнес-операция, что и по кнопке,
но выполненная роботом и убранная за собой. Пробы принципиально **не смотрят на
конфигурацию базы** («а какой сейчас `expireAfterSeconds`») — только на
поведение, поэтому обмануть индикатор нельзя.

| # | Индикатор | Что делает проба | Красный, когда |
| --- | --- | --- | --- |
| 1 | Сессии | держит контрольную сессию, созданную «постаревшей» на 2 минуты | сессия исчезла раньше, чем через 70 с |
| 2 | Заказы | запрос витрины с `hint` + контрольный `countDocuments` без него | витрина пустая, а заказы в работе есть |
| 3 | Регистрация | вставляет синтетического клиента (имя из пула, почта `monitoring+<ts>@crm.local`) и удаляет | вставка упала |
| 4 | Профили | прогоняет арифметику карточки по всем клиентам | агрегация упала |
| 5 | Хранилище | `$collStats` по `messages`: `totalIndexSize` | размер индексов > 15 МБ → 🟡 |
| 6 | Инциденты | создает синтетический инцидент, переводит в `Active`, удаляет | обновление не прошло валидацию |
| 7 | Поддержка | вставляет синтетическое обращение без `additionalInfo` и удаляет | вставка не прошла валидацию |

Все синтетические документы помечены `_synthetic: true` и удаляются в том же
цикле; остатки подчищаются при старте монитора и при `reset`. Демо-данные, с
которыми работает участник, пробы не трогают.

**Ошибку пробы страница не показывает.** Индикатор дает цвет и короткий факт;
реальный текст ошибки участник получает, нажав кнопку в левой панели. Это
осознанное решение: правая панель — глазами бизнеса, левая — глазами инженера.
В логах бэкенда ошибка пробы печатается один раз на смену состояния — как лог
обычного мониторинга.

### Проба сессий и ее тайминг

Единственная проба, которой нужно время. Контрольная сессия создается с
`createdAt = now − 2 минуты`: с часовым сроком жизни она это переживет, с
минутным — нет. Дальше:

- сессия исчезла раньше 70 с → 🔴 (`контрольная сессия прожила 60 с`);
- сессия дожила до 70 с → 🟢 (`контрольная сессия держится`);
- сессия дожила до 10+ минут и потом исчезла → это штатное протухание по сроку,
  проба молча создает новую и остается 🟢.

Поэтому после починки TTL плашка зеленеет не мгновенно, а в течение ~70 секунд:
70 с — это запас над периодом TTL-монитора MongoDB, который просыпается раз в
минуту. Все это время плашка пишет «проверяем, еще N с».

### Задержки

| Событие | Через сколько видно |
| --- | --- |
| Починены 2, 3, 4, 5, 6, 7 | ≤ 5 с (следующий цикл проб) |
| Починен 1 (TTL) | ≤ 70 с — ждем, переживет ли контрольная сессия проход TTL-монитора |

### Slack-движок

Лента — сценарный движок с состоянием на каждый индикатор:

```
проба 🔴/🟡 впервые ──> тред жалобы (Support / Sales / QA / DevOps / Product)
инцидент красный > 10 мин ──> эскалация («есть прогресс? клиенты пишут»)
переход 🔴 → 🟢 ──> благодарность от того же коллеги
переход 🟢 → 🔴 ──> «оно опять упало» (регресс тоже виден)
все 🟢 ──> финальное сообщение от тимлида
```

Лента живет в памяти бэкенда (не в `crm`) — иначе участник наткнется на нее в
`show collections` и прочитает спойлеры. Первые сообщения проставляются задним
числом (окно ~20 минут), поэтому на старте лента выглядит как утренняя переписка,
а не как пачка сообщений в одну секунду. После рестарта бэкенда лента
восстанавливается по текущему состоянию проб.

### API стенда

```
GET  /api/stand/status?since=<id>   индикаторы, метрики, состояние установки
                                    и новые сообщения ленты (одним запросом)
GET  /api/stand/connection          готовая строка подключения к базе
POST /api/stand/reset               переустановить стенд (данные + поломки)
```

`connection` собирает строку из того адреса, по которому открыта страница: зашли
на `http://192.168.1.50:8080` — получите `mongodb://…@192.168.1.50:27017/crm`, и
эту строку можно сразу отдать коллеге в той же сети. Если стенд живет за
пробросом или под доменным именем, адрес фиксируется переменной
`STAND_PUBLIC_HOST` в `.env`.

## 7. Команды починки (`mongosh`)

Вход участника:

```bash
docker compose exec mongo mongosh -u engineer -p engineer_secret \
        --authenticationDatabase crm crm
# или снаружи: mongosh "mongodb://engineer:engineer_secret@localhost:27017/crm"
```

**1. Сессии — TTL.**

```js
db.sessions.getIndexes()                       // expireAfterSeconds: 60
db.runCommand({ collMod: "sessions",
  index: { name: "ttl_createdAt", expireAfterSeconds: 3600 } })
// ответ: { expireAfterSeconds_old: 60, expireAfterSeconds_new: 3600, ok: 1 }
```

**2. Заказы — частичный индекс.**

```js
db.orders.getIndexes()                          // partialFilterExpression с чужими статусами
db.orders.countDocuments({ status: { $in: ["Open", "Pending"] } })   // а заказы-то есть
db.orders.dropIndex("orders_open")
db.orders.createIndex(
  { status: 1, createdAt: -1 },
  { name: "orders_open",
    partialFilterExpression: { status: { $in: ["Open", "Pending"] } } })
```

**3. Регистрация — уникальный индекс.**

```js
db.customers.getIndexes()                       // uniq_firstName: { unique: true }
db.customers.dropIndex("uniq_firstName")
db.customers.getIndexes()                       // uniq_email на месте — бизнес-ключ не потеряли
```

**4. Профили — тип поля.**

```js
db.customers.find({ age: { $type: "string" } }, { firstName: 1, age: 1 })
db.customers.updateMany(
  { age: { $type: "string" } },
  [{ $set: { age: { $toInt: "$age" } } }])      // update с pipeline
```

**5. Хранилище — бесполезный индекс.**

```js
db.messages.aggregate([{ $collStats: { storageStats: {} } }])[0]
        .storageStats.indexSizes                // messageText_1 ≈ 47 МБ
db.messages.dropIndex("messageText_1")
```

**6. Инциденты — enum валидатора.**

```js
db.getCollectionInfos({ name: "incidents" })[0].options.validator
db.runCommand({ collMod: "incidents", validator: { $jsonSchema: {
  bsonType: "object",
  title: "Инцидент CRM",
  required: ["code", "title", "status", "openedAt"],
  properties: {
    code:     { bsonType: "string" },
    title:    { bsonType: "string" },
    status:   { enum: ["New", "Active", "Resolved"] },
    owner:    { bsonType: "string" },
    openedAt: { bsonType: "date" }
  }
}}})
```

**7. Поддержка — лишнее `required`.**

```js
db.getCollectionInfos({ name: "tickets" })[0].options.validator
db.runCommand({ collMod: "tickets", validator: { $jsonSchema: {
  bsonType: "object",
  title: "Обращение в поддержку",
  required: ["subject", "body", "status", "createdAt"],   // additionalInfo убрано
  properties: {
    subject:        { bsonType: "string" },
    body:           { bsonType: "string" },
    additionalInfo: { bsonType: "string" },
    status:         { enum: ["Open", "Answered", "Closed"] },
    customerId:     { bsonType: "objectId" },
    createdAt:      { bsonType: "date" }
  }
}}})
```

Общий диагностический набор:

```js
db.getCollectionNames()
db.<coll>.getIndexes()
db.getCollectionInfos({ name: "<coll>" })[0].options.validator
db.<coll>.findOne()                             // какие поля и какие ТИПЫ
db.<coll>.find(...).explain("executionStats")   // какой индекс реально использован
```

## 9. Запуск и диагностика

```bash
cd scenarios/02-mongodb-dubug
cp .env.example .env
docker compose up --build
```

Первая сборка образа дольше прежней: в ней собирается фронтенд (npm install +

подхватываются на лету без пересборки.

Выбор активных инцидентов — переменная `STAND_INCIDENTS` в `docker-compose.yml`
(по умолчанию `1,2,3,4,5,6,7`, пустая строка — эталонный стенд без поломок).
Переустановка на ходу:

```bash
curl -s -X POST http://localhost:8080/api/stand/reset
```

### Как читать сбой

1. Прочитай жалобу в Slack — она задает, **на какую вкладку идти и какую кнопку
   жать**.
2. Нажми кнопку и прочитай сырой ответ: код ошибки MongoDB (`11000` —
   уникальность, `121` — валидация, `TypeMismatch` — тип значения) и `errInfo`
   называют класс проблемы, но не место.
3. Пустой ответ без ошибки — тоже симптом. Сверь с `mongosh`: `countDocuments`
   тем же фильтром и `explain()` того же запроса.
4. Смотри на объекты базы, а не только на документы: `getIndexes()`,
   `getCollectionInfos().options.validator`, `$collStats`.
5. Почини командой базы и подожди цикл монитора (5 с; для сессий — до 70 с).

## 10. Что изменилось относительно прошлой версии стенда

| Было (Ops-консоль) | Стало (Mongo Rescue Simulator) |
| --- | --- |
| 12 багов в `.env`, `console.controller.ts`, `db.config.ts` | 7 инцидентов, все внутри MongoDB |
| Участник правит файлы, приложение перезапускается | Участник правит базу, рестартов нет вообще |
| Индексы синхронизируются приложением из `db.config.ts` | Приложение не создает индексов; база — единственный источник правды |
| Симптом = красная плашка с ошибкой запроса | Симптом = жалоба коллеги в Slack + цвет бизнес-индикатора |
| Три «истории дежурного» в колонку | Две панели: действия слева, бизнес справа |
| Статус = «последний запрос страницы не упал» | Статус = синтетическая проба бизнес-операции раз в 5 с |
| Демо-данные пересоздаются при каждом старте | Установка однократная, переустановка — по кнопке |
| Два пользователя MongoDB, разница в правах — часть багов | Три пользователя: приложение, установщик, участник |

Переиспользовано без изменений: конверт ответов (`envelope.ts`), идея
административного подключения (`admin.ts`), сборка бэкенда, темная палитра
страницы.

### Что изменилось внутри самого симулятора

| Было | Стало |
| --- | --- |
| Одна HTML-страница на чистом JS, семь групп кнопок в колонку | React + Ant Design, пять вкладок по бизнес-областям |
| Клик по кнопке сразу отправлял запрос | Все, что пишет в базу, — через модалку с формой и подтверждением |

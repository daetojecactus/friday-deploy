# Mongo Rescue Simulator — техническая справка

> Справка по стенду: стек, структура, запуск, реестр инцидентов. Участникам для
> старта достаточно короткого [GUIDE.md](GUIDE.md).

Командный тренажер по MongoDB. Перед командой — работающее приложение (CRM
«Ориентир») и семь бизнес-инцидентов, причины которых лежат **внутри базы**:
индексы, TTL, `partialFilterExpression`, валидаторы схемы, тип значения в
документе, размер индекса.

Код приложения корректен и заблокирован. Единственный инструмент починки —
`mongosh`. Индикаторы на странице зеленеют сами: раз в 5 секунд синтетический
монитор выполняет каждую бизнес-операцию заново.

## Стек

- **Backend** — NestJS (TypeScript), нативный драйвер `mongodb`, без ORM.
  Осознанно: Mongoose синхронизировал бы индексы при старте и «чинил» бы стенд
  сам.
- **Frontend** — React 18 + Ant Design 5, сборка Vite. Слева симулятор действий
  пользователя (пять вкладок, формы в модалках), справа Production Status и
  Slack-лента; опрос раз в 3 секунды. Рабочая область помещается в один экран.
- **Инфраструктура** — Docker Compose: backend + MongoDB 7 (кэш WiredTiger
  урезан до 256 МБ). Бандл страницы собирается первой стадией
  `backend/Dockerfile` и отдается тем же бэкендом — отдельного веб-сервера нет.

## Быстрый старт

```bash
cp .env.example .env
docker compose up --build
```

Страница — http://localhost:8080. Первая сборка занимает около минуты (в ней
собирается фронтенд), дальше слои кэшируются. Первый старт — еще секунд десять:
стенд наполняется данными (60 клиентов, 800 заказов, 300 обращений, 3 000
сообщений переписки) и ломается по списку. Прогресс виден на странице.

База доступна снаружи и из локальной сети — порт `27017` опубликован на всех
интерфейсах машины:

```bash
mongosh "mongodb://engineer:engineer_secret@localhost:27017/crm"
```

Готовая строка подключения, которую можно скопировать и передать коллеге, лежит
на вкладке «Система» и в `GET /api/stand/connection`: адрес в ней подставляется
тот, по которому открыта страница. Если стенд живет за пробросом портов или под
доменным именем, адрес фиксируется переменной `STAND_PUBLIC_HOST` в `.env`.

## Реестр инцидентов

| # | Индикатор | Симптом | Причина в MongoDB |
| --- | --- | --- | --- |
| 1 | Сессии | Через минуту выкидывает из кабинета | TTL-индекс `sessions`: `expireAfterSeconds: 60` вместо `3600` |
| 2 | Заказы | Витрина заказов пустая, ошибки нет | перевернутый список статусов в `partialFilterExpression` индекса `orders_open` |
| 3 | Регистрация | `E11000 duplicate key error` | уникальный индекс на `customers.firstName` |
| 4 | Профили | 500 на одном конкретном клиенте | `age` — строка вместо числа в одном документе |
| 5 | Хранилище | «Монга съела память», операции работают | индекс `messages.messageText_1` по тексту на 47 МБ |
| 6 | Инциденты | `Document failed validation` при переводе в Active | опечатка `Actve` в `enum` валидатора |
| 7 | Поддержка | `Document failed validation` при отправке формы | `additionalInfo` попало в `required` |

Набор активных инцидентов задается переменной `STAND_INCIDENTS` в
`docker-compose.yml` (по умолчанию все семь; пустая строка — эталонный стенд без
поломок).

## Как это устроено

- **Установка однократная.** Маркер лежит в отдельной базе `stand_meta`, к
  которой у участника нет доступа. Рестарт бэкенда не трогает ни данные, ни
  починки. Переустановка — кнопкой на вкладке «Система» (с подтверждением
  вводом слова) или `POST /api/stand/reset`.
- **Приложение не создает индексов** и не знает схемы: схема, индексы и
  валидаторы живут только в MongoDB. Поэтому починка применяется мгновенно и
  ничем не перетирается.
- **Три пользователя базы:** `root` (установщик стенда), `crm_app`
  (приложение и пробы, `readWrite`), `engineer` (участник, `readWrite` +
  `dbAdmin`).
- **Индикаторы ставит поведение, а не конфиг.** Пробы не проверяют
  `expireAfterSeconds` — они выполняют бизнес-операцию и смотрят на результат.
- **О починке сообщает не чекер, а бизнес.** Переход 🔴/🟡 → 🟢 дает
  благодарность коллеги в чате и тост «Починено: …»; когда зеленеют все семь —
  финальное сообщение тимлида и тост «Продакшен полностью восстановлен».

## Про данные

- Все имена обезличены: клиенты CRM и коллеги в чате — персонажи кинематографа.
  Роли и связи сохранены (владельцы инцидентов — это авторы сообщений в ленте).
- Данные детерминированы: и первый старт, и любая пересборка дают одну и ту же
  базу.
- `docker compose down` данные сохраняет (именованный том `mongo_data`).
- `docker compose down -v` сносит все, следующий старт установит стенд заново.
- Синтетические документы проб помечены `_synthetic: true` и удаляются в том же
  цикле.

## Правила (кратко)

1. Работаем по очереди, решения принимает Капитан.
2. Правим **только базу** через `mongosh`. Файлы репозитория — эталон.
3. `backend/src/internal/` не открываем: там установщик и список поломок.

Полные правила — в [RULES.md](RULES.md), устройство стенда — в
[CONTEXT.md](CONTEXT.md).

## Для ведущего

Стенд ломает себя сам при первой установке. Что именно сломано, как это проверить
и как починить — в [SABOTAGE.md](SABOTAGE.md), включая точные тексты ошибок
MongoDB и наборы инцидентов для сессий разной длины.

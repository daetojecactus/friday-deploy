# Плейбук ведущего

> ⚠️ Спойлер. Здесь расписаны все семь инцидентов: что сломано, как это выглядит
> у команды, как проверить и как починить. Участникам не показывать.

Стенд ломает себя сам при первой установке — руками ничего готовить не нужно.
Список активных инцидентов задается переменной `STAND_INCIDENTS` в
`docker-compose.yml`:

```yaml
STAND_INCIDENTS: "1,2,3,4,5,6,7"   # по умолчанию все семь
STAND_INCIDENTS: "3,7,1"           # короткая сессия
STAND_INCIDENTS: ""                # эталонный стенд, все зеленое
```

Переменная применяется при установке. Чтобы поменять набор на ходу: правим
`docker-compose.yml`, `docker compose up -d backend`, затем «Пересобрать стенд»
на вкладке «Система» или `curl -X POST localhost:8080/api/stand/reset`.

## Подготовка

```bash
cd scenarios/02-mongodb-dubug
cp .env.example .env
docker compose up --build -d
```

Первая сборка — около минуты: в образ бэкенда встраивается собранный фронтенд
(React + Ant Design). Дальше слои кэшируются.

Через 10–15 секунд на странице должно быть шесть красных плашек и одна желтая
(«Хранилище»). Плашка «Сессии» краснеет через ~60 секунд — проба честно ждет
TTL-монитор.

Левая панель разложена по вкладкам, и жалоба в чате прямо указывает, куда идти:

| Вкладка | Инциденты | Что там жмут |
| --- | --- | --- |
| Клиенты | 3, 4 | «Заполнить карточку клиента», «Открыть карточку» |
| Заказы | 2 | ничего: витрина обновляется сама раз в 5 с |
| Доступ | 1 | «Войти в кабинет», «Выполнить GET /api/auth/me» |
| Поддержка | 6, 7 | «Заполнить обращение», «Выбрать инцидент и статус» |
| Система | 5 | строка подключения, «Собрать отчет», пересборка |

Все, что пишет в базу, отправляется из модалки с формой: поля заполнены
черновиком, но их видно и можно поменять — это удобно, когда команда хочет
проверить гипотезу («а если почта другая?», «а если заполнить все поля?»).

Доступы:

```bash
# участник
mongosh "mongodb://engineer:engineer_secret@localhost:27017/crm"

# root (ведущему; участнику не нужен)
docker compose exec mongo mongosh -u root -p root_secret \
        --authenticationDatabase admin crm
```

Раздать доступ команде: откройте стенд по адресу машины в сети
(`hostname -I` → `http://192.168.1.50:8080`) и отправьте коллегам ссылку. На
вкладке «Система» будет готовая строка `mongodb://engineer:…@192.168.1.50:27017/crm`
— адрес подставляется тот, по которому открыта страница, так что копировать
можно прямо из интерфейса. Если стенд за пробросом или под доменным именем,
пропишите адрес в `STAND_PUBLIC_HOST` в `.env`.

## 1. Сессии — TTL-индекс

**Что сломано.** `sessions.ttl_createdAt` пересоздан с `expireAfterSeconds: 60`
вместо `3600`.

**Что видит команда.** Support пишет, что клиентов выкидывает из кабинета через
минуту. На вкладке «Доступ» вход выдает токен (его возраст тикает рядом с
кнопкой), запрос под сессией сразу отвечает `200`, а через минуту —
`401 session expired`.

**Как проверить.**

```js
db.sessions.getIndexes()   // expireAfterSeconds: 60
```

**Починка.**

```js
db.runCommand({ collMod: "sessions",
  index: { name: "ttl_createdAt", expireAfterSeconds: 3600 } })
// { expireAfterSeconds_old: 60, expireAfterSeconds_new: 3600, ok: 1 }
```

Годится и `dropIndex` + `createIndex` с нужной опцией.

**Чему учит.** Срок жизни документа задается базой, а не приложением. Плюс
тайминг: TTL-монитор просыпается раз в минуту, поэтому сессия живет 60–120 секунд
и «ровно минуты» никогда не получается.

**Ловушки.** Плашка зеленеет не сразу, а за ~70 секунд — проба ждет прохода
TTL-монитора. Скажите об этом команде, иначе они решат, что фикс не сработал, и
откатят его. Подсказку про «сессия у нас живет час» дает продакт в чате — если
команда буксует, отправьте их перечитать ленту.

## 2. Заказы — частичный индекс

**Что сломано.** У индекса `orders_open` в `partialFilterExpression` перечислены
закрытые статусы: `{ status: { $in: ["Paid", "Shipped", "Closed"] } }` вместо
`["Open", "Pending"]`.

**Что видит команда.** Sales жалуется на пустую витрину. Вкладка «Заказы»
обновляется сама и раз в пять секунд показывает одно и то же: `200`,
`{ "ok": true, "data": [] }`, в таблице «витрина пустая» — ошибки нет вообще.
После починки список наполняется сам, кликать не нужно.

**Как проверить.**

```js
db.orders.getIndexes()                                          // чужие статусы в фильтре
db.orders.countDocuments({ status: { $in: ["Open","Pending"] } })  // ~110, заказы на месте
```

**Починка.**

```js
db.orders.dropIndex("orders_open")
db.orders.createIndex(
  { status: 1, createdAt: -1 },
  { name: "orders_open",
    partialFilterExpression: { status: { $in: ["Open", "Pending"] } } })
```

**Чему учит.** Частичный индекс содержит не все документы, и запрос,
зафиксированный через `hint`, видит ровно то, что лежит в индексе. Отсутствие
ошибки не означает отсутствие проблемы.

**Ловушки.** Если команда удалит индекс и не пересоздаст, витрина начнет падать с
`BadValue: hint provided does not correspond to an existing index` — это прогресс,
а не регресс: имя индекса обязано остаться прежним. И еще: `$nin` в
`partialFilterExpression` MongoDB не поддерживает, поэтому «просто поменять
оператор» не выйдет — нужен правильный список внутри `$in`.

## 3. Регистрация — уникальный индекс не на том поле

**Что сломано.** На `customers.firstName` создан `uniq_firstName` с
`unique: true`.

**Что видит команда.** Форма регистрации подставляет имя из существующего пула
(почта при этом всегда уникальная) и получает:

```
E11000 duplicate key error collection: crm.customers index: uniq_firstName
dup key: { firstName: "Винсент" }
```

**Как проверить.**

```js
db.customers.getIndexes()   // uniq_firstName и uniq_email рядом
```

**Починка.**

```js
db.customers.dropIndex("uniq_firstName")
```

**Чему учит.** Читать `E11000` целиком: в тексте прямо назван индекс и ключ.
Отличать бизнес-ключ (почта) от совпадения по имени.

**Ловушки.** Соблазн снести заодно `uniq_email` — «чтобы наверняка». Спросите,
что тогда произойдет с дубликатами клиентов.

## 4. Профили — тип значения в документе

**Что сломано.** У четвертого по счету клиента `age` записан строкой (`"34"`).
В обезличенной базе это **Бутч Кулидж** — четвертый в выпадающем списке.

**Что видит команда.** Карточки открываются у всех, кроме одного:

```
MongoServerError 14 TypeMismatch
PlanExecutor error during aggregation :: caused by :: can't $subtract string from int
```

**Как проверить.**

```js
db.customers.find({ age: { $type: "string" } }, { firstName: 1, age: 1 })
```

**Починка.**

```js
db.customers.updateMany(
  { age: { $type: "string" } },
  [{ $set: { age: { $toInt: "$age" } } }])
```

**Чему учит.** MongoDB не типизирует поля сама: там, где нет валидатора, в
числовом поле спокойно живет строка. Ошибку кидает база, а не приложение, —
«поправить код» физически нечего.

**Ловушки.** Правка через `$set: { age: 34 }` руками тоже сработает, но спросите,
что делать, если таких документов тысяча. Это подводит к update с pipeline и к
разговору о валидаторе, которого у `customers` нет.

## 5. Хранилище — бесполезный индекс

**Что сломано.** Создан индекс `messages.messageText_1` по тексту сообщения
(~16 КБ на документ). Весит ~47 МБ при 41 МБ данных.

**Что видит команда.** Единственный инцидент без падающей ручки: все операции
работают. Есть жалоба DevOps в чате и желтая плашка «Хранилище». Кнопка «Собрать
отчет» на вкладке «Система» показывает размеры по коллекциям (`messages`:
41 МБ данных против 47 МБ индексов), а размеры каждого индекса по отдельности —
в сыром ответе, поле `indexSizes`.

**Как проверить.**

```js
db.messages.aggregate([{ $collStats: { storageStats: {} } }])[0].storageStats.indexSizes
// { _id_: ..., ticket_thread: ~0.1 МБ, messageText_1: ~47 МБ }
```

**Починка.**

```js
db.messages.dropIndex("messageText_1")
```

**Чему учит.** Индексы стоят памяти и места, а неиспользуемый индекс — чистый
убыток. Кэш инстанса урезан до 256 МБ, поэтому 47 МБ мусора — это заметная доля,
и разговор получается предметным.

**Ловушки.** Команда может решить, что дело в объеме данных. Хорошее направление
для обсуждения: как понять, что индекс не используется (какие запросы вообще
делает приложение, `explain()`, `$indexStats`).

## 6. Инциденты — опечатка в enum валидатора

**Что сломано.** В валидаторе `incidents` статус описан как
`enum: ["New", "Actve", "Resolved"]`.

**Что видит команда.**

```
MongoServerError 121 DocumentValidationFailure
Plan executor error during findAndModify :: caused by :: Document failed validation
errInfo: { ... "operatorName": "enum", "specifiedAs": { "enum": ["New","Actve","Resolved"] } ... }
```

**Как проверить.**

```js
db.getCollectionInfos({ name: "incidents" })[0].options.validator
```

**Починка.** Полный `collMod` с эталонной схемой — см. раздел 7 в
[CONTEXT.md](CONTEXT.md#7-команды-починки-mongosh).

**Чему учит.** Валидатор — объект базы, а не код. Читать `errInfo`: там написано,
какое правило не прошло и какие значения разрешены.

**Ловушки.** `collMod` заменяет валидатор целиком, а не патчит его. Если команда
отправит только `properties.status`, остальные правила пропадут — хороший повод
поговорить про то, что схема здесь не мигрируется по кусочкам.

## 7. Поддержка — лишнее поле в required

**Что сломано.** В валидаторе `tickets` в `required` добавлено `additionalInfo`.

**Что видит команда.** Та же `DocumentValidationFailure`, но `errInfo` другой:

```
"required": ["subject","body","status","createdAt","additionalInfo"],
"missingProperties": ["additionalInfo"]
```

Черновик формы приходит с пустой «дополнительной информацией» — и падает. Если в
модалке это поле заполнить, обращение уходит: разница видна за два клика и прямо
указывает на поле.

**Как проверить.**

```js
db.getCollectionInfos({ name: "tickets" })[0].options.validator
```

**Починка.** `collMod` с эталонной схемой (без `additionalInfo` в `required`).

**Чему учит.** Пара 6 и 7 — про то, что одинаковый заголовок ошибки не означает
одинаковую причину. Разницу видно только в `errInfo`.

**Ловушки.** Самый простой инцидент на стенде: одно и то же обращение с полем и
без него дает разный результат. Хорош как разминка в начале.

## Рекомендованные наборы

| Формат | `STAND_INCIDENTS` | Почему |
| --- | --- | --- |
| Разминка, 20–30 минут | `7,3` | оба инцидента читаются прямо из текста ошибки |
| Стандарт, 45–60 минут | `7,3,6,2` | добавляются валидатор целиком и «пустой ответ без ошибки» |
| Полный, 1,5 часа | `1,2,3,4,5,6,7` | все семь, включая тайминг TTL и разговор про память |
| Про производительность | `5,2` | индексы: бесполезный и неправильный |
| Про схему и типы | `6,7,4` | валидаторы и типы значений |

Порядок в переменной не важен: инциденты независимы, домино нет.

## Чему учит каждый инцидент (шпаргалка)

| # | Класс проблемы | Навык |
| --- | --- | --- |
| 1 | TTL-индекс | срок жизни данных задается базой; поведение TTL-монитора |
| 2 | частичный индекс + `hint` | индекс содержит не все документы; пустой ответ без ошибки |
| 3 | уникальный индекс | читать `E11000`; отличать бизнес-ключ от совпадения |
| 4 | тип значения | MongoDB не типизирует поля; ошибки агрегации |
| 5 | стоимость индекса | индексы стоят памяти; неиспользуемый индекс — убыток |
| 6 | валидатор, `enum` | схема — объект базы; `collMod` заменяет ее целиком |
| 7 | валидатор, `required` | читать `errInfo`, а не заголовок ошибки |

### Что с чем не путать

- **6 против 7.** Одинаковая ошибка `Document failed validation`, разные правила
  внутри `errInfo`: `enum` против `required`.
- **2 против 5.** Оба про индексы, но 2 — это неправильный индекс, который
  используется, а 5 — правильный по форме индекс, который не используется никогда.
- **1 против 4.** Оба выглядят как «приложение сломалось на ровном месте», но 1 —
  это фоновый процесс базы, а 4 — конкретный документ.
- **2 против «данные потерялись».** Заказы на месте, `countDocuments` это
  доказывает за секунду. Первым делом — сверка экрана с базой.

# посмотреть, что делает мониторинг

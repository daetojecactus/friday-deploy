# Friday Deploy — набор командных тренажёров по траблшутингу

Это набор мини-тренажёров для тех-стендапа. Каждый тренажёр («сценарий») —
самостоятельная песочница со своей задачей, своим стеком и своим
`docker-compose`. Ведущий заранее ломает часть системы, команда чинит её по
очереди на живом стенде.

Общий формат и правила урока одинаковы для всех сценариев (см. ниже). Всё, что
специфично для конкретного тренажёра — стек, список проверок, как ломать и
чинить — лежит внутри его папки.

## Сценарии

| #   | Папка                                                              | Тема                                                 | Стек              |
| --- | ----------------------------------------------------------------- | ---------------------------------------------------- | ----------------- |
| 01  | [`scenarios/01-healthcheck-debug/`](scenarios/01-healthcheck-debug/) | Дашборд из 10 healthcheck'ов — сделать все зелёными | NestJS + PG + Redis + Mongo |
| 02  | [`scenarios/02-mongodb-dubug/`](scenarios/02-mongodb-dubug/)       | Ops-консоль дежурного — оживить сломанную связку с MongoDB | NestJS + MongoDB |

Новые сценарии добавляются как отдельные папки в `scenarios/` с собственным
`README.md` и `docker-compose.yml`. Стек может быть любым (Node, Python и т.д.) —
корень репозитория про внутренности сценария ничего не знает.

## Как запустить сценарий

Сценарии рассчитаны на запуск **по одному за раз** (каждый занимает порт 8080):

```bash
cd scenarios/01-healthcheck-debug   # или scenarios/02-mongodb-dubug
cp .env.example .env
docker compose up --build           # на старых установках: docker-compose
```

Страница сценария открывается на **http://localhost:8080**. Подробности,
список проверок и плейбук ведущего — в `README.md` и `SABOTAGE.md` внутри
папки сценария. Сценарий 02 отличается механикой: вместо дашборда с чеками —
живое приложение без автоматических проверок, которое оживает по мере починки.

## Общие правила урока

1. Работаем по очереди.
2. Говорит и принимает решения только **Капитан**.
3. Правим только то, что относится к «нашей стороне» (обычно `.env` и исходники
   бэкенда). Инфраструктуру (`docker-compose.yml`, `Dockerfile`, зависимости) —
   только с общего согласия команды.
4. Точный список того, что правим и какими командами диагностируем, — в
   `RULES.md` конкретного сценария.
